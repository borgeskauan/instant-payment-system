# Load-test quiescence through Kafka lag

## Purpose

Reduce database coupling in the load-test runner by removing preventive PostgreSQL cleanup. The runner will continue using its existing Kafka-lag preflight as a best-effort indication that the shared test environment is ready.

This design deliberately accepts that Kafka lag is a heuristic, not a formal proof that every internal queue is empty.

## Scope

The runner will continue checking, once before the run:

- the SPI payment-request consumer group on the `spi-payment-requests` topic;
- the SPI status-report consumer group on the `spi-payment-status-reports` topic;
- the notification-gateway consumer group on the `psp-notifications` topic.

The run will be refused when any checked lag is nonzero or cannot be read. No stability window or repeated sampling will be introduced.

## PostgreSQL cleanup removal

The runner will no longer connect directly to PostgreSQL or truncate persistent state before a run. The following runner surface will be removed:

- `POSTGRES_CONTAINER`, `POSTGRES_USER` and `POSTGRES_DB` settings used by state reset;
- `RESET_TEST_STATE` state;
- `--reset-state` and `--no-reset-state`;
- `reset_persistent_test_state_if_enabled` and its invocation;
- `reset-test-state.log`;
- shell tests that prescribe the `psql` command and physical table names.

This removal does not affect the opt-in `--postgres-statements` diagnostic. That diagnostic remains separate from environment preparation and can be reconsidered independently.

## Preserved behavior

Fund provisioning remains enabled by default and continues through the SPI administrative HTTP API. The Go load-tool and report continue using only the profile snapshot, resolved execution plan, run window and generated event artifacts; they do not query PostgreSQL.

Historical payments, audit events, published outbox entries and acknowledged deliveries remain in the database. This avoids permanently exercising an artificially empty database and removes knowledge of service-owned tables from the load-test flow.

## Residual contamination

Kafka lag cannot expose an SPI outbox entry that has not yet been published or a notification delivery already persisted by the gateway. Residual work can therefore remain undetected and add load to a new run. This is an accepted limitation of the selected heuristic.

The runner only refuses a run based on the Kafka-lag checks described above. This change adds no automatic detection, classification or invalidation of residual work. Payment identifiers remain unique per run and report outcomes remain correlated to payments generated by the current execution, which prevents stale payment identifiers from being attributed to current outcomes but does not prove that the environment was quiescent.

## Verification

Automated checks will prove that:

- the public runner no longer accepts reset-state flags;
- the normal runner path does not invoke `psql` for state cleanup;
- nonzero or unreadable Kafka lag still fails before funding and load generation;
- zero lag still permits the runner to continue;
- fund provisioning remains unchanged;
- shell syntax, existing shell tests and Go tests remain valid.

No service observability endpoint, coordinated barrier, repeated lag sampling or database cleanup replacement is part of this change.
